# GNOME 50 and 51 Port Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Make Open Bar load and run on GNOME Shell 50 and 51, fix the three defects in its GNOME 49+ code path, and leave behind a reproducible way to prove it.

**Architecture:** Two logical commits on `feat/main/gnome-51-support`. The first restores a four-line fix upstream shipped on extensions.gnome.org but never pushed to git, so it can be offered upstream on its own. The second widens `shell-version`, corrects the two silent theming defects, and guards the DateMenu traversal so future Shell drift degrades one menu instead of aborting `enable()`. A headless Shell harness, built first, is what every later task is measured against.

**Tech Stack:** GJS (ESM, GNOME 45+ extension API), GNOME Shell 51.1, GTK 4.24.1 / libadwaita 1.10 for preferences, POSIX shell for the harness, ESLint with `eslint-config-gnome`.

**Spec:** `docs/superpowers/specs/2026-10-22-gnome-51-port-design.md`

## Global Constraints

- Licence: every source file keeps its `SPDX-License-Identifier: GPL-2.0-or-later` header and the `author: neuromorph` attribution. Never strip or rewrite them.
- `shell-version` target value, verbatim: `["45", "46", "47", "48", "49", "50", "51"]`.
- `metadata.json` `version` target value: `50`.
- Code files carry no comments. What a comment would say goes in a function name or under `docs/`. Comments removed from upstream code must have their content land in `docs/` in the same commit.
- Functions are small and named to document themselves.
- Functional style by default.
- Only code this port touches is brought into line with the above. Upstream code left untouched stays as it is.
- Shell scripts pass `shellcheck` and `shfmt -d`.
- The interactive shell on this workstation is fish. Any command beyond a simple `&&`/`|` chain is wrapped in `sh -c '…'`. No heredocs, no `$?` (use `$status`), no `for … do … done` at the fish prompt.
- Extension state is read from the Shell via `org.gnome.Shell.Extensions.GetExtensionInfo` on `/org/gnome/Shell`, never from the `gnome-extensions` CLI.
- `ExtensionState` numbers (`misc/extensionUtils.js:15-28`): 1 `ACTIVE`, 2 `INACTIVE`, 3 `ERROR`, 4 `OUT_OF_DATE`, 6 `INITIALIZED`.
- State 6 `INITIALIZED` from the harness is a harness failure, not a test result: the extension was never enabled and nothing downstream was measured.

## Points à valider

| Decision | Proposition | Alternative |
|---|---|---|
| Harness location | `tools/verify-headless.sh`, mirroring gnome-shell's own `tools/` directory | A `tests/` tree, which would imply a test runner the project does not have |
| Unsafe-mode helper | A throwaway `unsafemode@local` extension under `tools/harness/`, installed only into the harness's scratch `XDG_DATA_HOME` | Patch `global.context.unsafe_mode` from inside Open Bar under a debug flag, which would ship test code in the product |
| Defect 2 and 3 assertions | `org.gnome.Shell.Eval`, reachable because of that helper | Screenshot comparison, which cannot see style classes |
| Task 6 scope | Extract the DateMenu traversal into named methods *and* guard it, in one commit | Guard only, leaving a 55-line inline block that the no-comment rule cannot be applied to |
| Defect 3 target | Resolve the themed actors by style class, since every stylesheet rule is the compound `.openmenu.message` | Resolve by tree position — what rounds 3 and 4 of the spec specified, and what the live tree disproved |
| Group chrome CSS | Out of scope, documented and ticketed separately | Extend `stylesheets.js` here |

- [ ] **Step 2: Write the harness script**

`tools/verify-headless.sh`:

```sh
#!/bin/sh
set -eu

UUID=openbar@neuromorph
HELPER=unsafemode@local
REPO=$(CDPATH='' cd -- "$(dirname -- "$0")/.." && pwd)

widen_metadata=yes
mutate_expr=''
eval_js=''

while [ $# -gt 0 ]; do
    case $1 in
    --as-is) widen_metadata=no ;;
    --mutate)
        mutate_expr=$2
        shift
        ;;
    --eval)
        eval_js=$2
        shift
        ;;
    *)
        echo "unknown option: $1" >&2
        exit 2
        ;;
    esac
    shift
done

work=$(mktemp -d)
trap 'rm -rf "$work"' EXIT

prepare_session_dirs() {
    XDG_DATA_HOME="$work/data"
    XDG_CONFIG_HOME="$work/config"
    XDG_CACHE_HOME="$work/cache"
    XDG_RUNTIME_DIR="$work/run"
    GSETTINGS_BACKEND=keyfile
    export XDG_DATA_HOME XDG_CONFIG_HOME XDG_CACHE_HOME XDG_RUNTIME_DIR GSETTINGS_BACKEND
    mkdir -p "$XDG_DATA_HOME/gnome-shell/extensions" \
        "$XDG_CONFIG_HOME/glib-2.0/settings" "$XDG_CACHE_HOME" "$XDG_RUNTIME_DIR"
    chmod 700 "$XDG_RUNTIME_DIR"
}

install_payload() {
    cp -r "$REPO/$UUID" "$XDG_DATA_HOME/gnome-shell/extensions/$UUID"
    cp -r "$REPO/tools/harness/$HELPER" "$XDG_DATA_HOME/gnome-shell/extensions/$HELPER"
}

widen_scratch_metadata() {
    [ "$widen_metadata" = yes ] || return 0
    metadata="$XDG_DATA_HOME/gnome-shell/extensions/$UUID/metadata.json"
    running_major=$(gnome-shell --version | sed 's/[^0-9]*\([0-9]*\).*/\1/')
    python3 -I -c '
import json, sys
path, major = sys.argv[1], sys.argv[2]
with open(path) as handle:
    meta = json.load(handle)
if major not in meta["shell-version"]:
    meta["shell-version"].append(major)
with open(path, "w") as handle:
    json.dump(meta, handle, indent=2)
' "$metadata" "$running_major"
}

mutate_scratch_source() {
    [ -n "$mutate_expr" ] || return 0
    sed -i "$mutate_expr" "$XDG_DATA_HOME/gnome-shell/extensions/$UUID/extension.js"
}

enable_extensions() {
    gsettings set org.gnome.shell disable-user-extensions false
    gsettings set org.gnome.shell enabled-extensions "['$HELPER', '$UUID']"
    [ "$(gsettings get org.gnome.shell enabled-extensions)" != '@as []' ] ||
        fail 'gsettings writes are not persisting; the keyfile backend is not in effect'
}

start_shell() {
    WAYLAND_DISPLAY="openbar-verify-$$"
    export WAYLAND_DISPLAY
    gnome-shell --headless --virtual-monitor 1280x720 >"$work/shell.log" 2>&1 &
    shell_pid=$!
    waited=0
    while [ "$waited" -lt 40 ]; do
        if shell_version >/dev/null 2>&1; then return 0; fi
        sleep 1
        waited=$((waited + 1))
    done
    fail 'the test Shell never answered on the session bus'
}

shell_version() {
    gdbus call --session -d org.gnome.Shell -o /org/gnome/Shell \
        -m org.freedesktop.DBus.Properties.Get org.gnome.Shell ShellVersion
}

extension_field() {
    gdbus call --session -d org.gnome.Shell -o /org/gnome/Shell \
        -m org.gnome.Shell.Extensions.GetExtensionInfo "$UUID" |
        tr ',' '\n' | sed -n "s/.*'$1': <\(.*\)>.*/\1/p" | head -1
}

shell_eval() {
    gdbus call --session -d org.gnome.Shell -o /org/gnome/Shell \
        -m org.gnome.Shell.Eval "$1"
}

fail() {
    echo "FAIL: $1" >&2
    [ -n "${shell_pid:-}" ] && kill "$shell_pid" 2>/dev/null
    exit 1
}

report() {
    state=$(extension_field state)
    error=$(extension_field error)
    echo "shell: $(shell_version)"
    echo "state: $state"
    echo "error: $error"
    [ "$state" != '6.0' ] ||
        fail 'state INITIALIZED: the extension was never enabled, nothing was measured'
    [ -n "$eval_js" ] && echo "eval: $(shell_eval "$eval_js")"
    stylesheet="$XDG_RUNTIME_DIR/io.github.neuromorph.openbar/stylesheet.css"
    [ -f "$stylesheet" ] && echo "stylesheet: generated" || echo "stylesheet: absent"
    grep -c 'Openbar: Error loading stylesheet' "$work/shell.log" |
        sed 's/^/stylesheet load errors: /'
    grep -E 'JS ERROR' "$work/shell.log" | head -5 || true
    [ "$state" = '1.0' ]
}

prepare_session_dirs
install_payload
widen_scratch_metadata
mutate_scratch_source
enable_extensions
start_shell
sleep 8
report
status=$?
kill "$shell_pid" 2>/dev/null
exit "$status"
```

- [ ] **Step 5: Write the testing documentation**

`docs/development/testing.md`:

```markdown
# Verifying a change against a real Shell

`tools/verify-headless.sh` starts a throwaway GNOME Shell, installs this
extension into a scratch `XDG_DATA_HOME`, enables it, and reports the state the
Shell itself assigns it. It touches nothing in the session you are logged into
and opens no window.

    dbus-run-session -- ./tools/verify-headless.sh

Exit 0 means the Shell reached state 1 `ACTIVE` with an empty error.

## Options

| Option | Effect |
|---|---|
| `--as-is` | Do not widen `shell-version` in the scratch copy. Used to assert that an unsupported declaration is refused. |
| `--mutate SED_EXPR` | Apply a `sed -i` expression to the scratch `extension.js` before launch. Used to inject a fault and confirm a guard catches it. |
| `--eval JS` | Evaluate one expression inside the test Shell after the state check and print the result. |

## Why it is built this way

Two properties are load-bearing, and both were found by watching an earlier
version of this harness report success while measuring nothing.

`GSETTINGS_BACKEND=keyfile` is mandatory. Under `dbus-run-session` there is no
activatable dconf service, so `gsettings set` fails silently,
`enabled-extensions` reads back as `@as []`, the extension is never enabled, and
it sits at state 6 `INITIALIZED` while every downstream assertion passes
vacuously. The harness therefore treats state 6 as a failure of itself.

State is read from the Shell over
`org.gnome.Shell.Extensions.GetExtensionInfo` on `/org/gnome/Shell`, not from
the `gnome-extensions` CLI. That CLI can be answered by a standalone,
D-Bus-activated `org.gnome.Shell.Extensions` service which scans the disk, so it
reports plausible states while the Shell is dead.

## Inspecting the actor tree

`--eval` works because the harness also installs
`tools/harness/unsafemode@local`, a two-line extension that sets
`global.context.unsafe_mode = true` so `org.gnome.Shell.Eval` answers.
`global.context.unsafe_mode` cannot be set from outside the Shell, and
`Eval` returns `(false, '')` without it.

`Main` is in scope for evaluated code, because `js/ui/shellDBus.js` imports it.

The helper is installed only into the scratch directory. It is never part of a
release.

## States

`ExtensionState`, from `js/misc/extensionUtils.js`:

| Number | Name |
|---|---|
| 1 | `ACTIVE` |
| 2 | `INACTIVE` |
| 3 | `ERROR` |
| 4 | `OUT_OF_DATE` |
| 6 | `INITIALIZED` |
```

EXPR
sh -c 'dbus-run-session -- ./tools/verify-headless.sh --as-is --eval "$(cat /tmp/openbar-probe.js)"'

Expected, and observed by the plan's author on Shell 51.1 before this task was written: exit 0, and

```

    applySectionStyles(list, add) {
        this.trackMessageAdditions(list, add);

        this.messageActors(list).forEach(message => {
            this.applyMenuClass(message, add);
        });
    }

    trackMessageAdditions(list, add) {
        if(!add) {
            this.untrackMessageAdditions();
            return;
        }

        this.messageContainers(list).forEach(container => {
            if(this.msgLists.includes(container))
                return;

            this.msgLists.push(container);
            this.msgListIds.push(container.connect(this.addedSignal, () => {
                this.applySectionStyles(list, add);
            }));
        });
    }

    untrackMessageAdditions() {
        this.msgLists.forEach((container, idx) => {
            if(this.msgListIds[idx])
                container.disconnect(this.msgListIds[idx]);
        });

        this.msgLists = [];
        this.msgListIds = [];
    }
```

Three things to understand about this shape rather than transcribe blindly:

- **`has_style_class_name?.(...)` needs its optional call.** `MessageView` holds a non-message `_overlay` child which is a plain `Clutter.Actor`, and that method only exists on `St.Widget`. Without `?.` the walk throws on the first child it meets.
- **`messageActors` stops descending at the first match**, so a `message` actor's own children are not collected. `messageContainers` is its complement: every actor on the way down, excluding the messages themselves. Those are what can gain children, which is why they are what gets connected.
- **The arrays are the existing ones.** `msgLists` and `msgListIds` are already initialised at `:1390-1391` and already disconnected in `disable()` at `:1618-1628`, which guards `this.msgListIds[i] > 0`. Keeping them parallel means that existing cleanup keeps working and is not duplicated.

The `includes` guard is what stops a second connection to a container already tracked, since `applySectionStyles` is re-entered from the very signal it connects. The handler adds no children, so it does not re-trigger itself.

```markdown
# The date menu's message list, before and after GNOME 49

Open Bar puts its `openmenu` class on the actors it themes. The date menu's
message list changed shape in GNOME 49, and the change is deeper than it looks.

    up to 48:  sectionList -> section -> section._list -> St.Bin -> .child = Message

    since 49:  MessageView                         message-view
                 +- St.Bin
                      +- NotificationMessageGroup  message-notification-group
                           +- <container>
                           |    +- NotificationMessage   message
                           +- St.BoxLayout         message-group-header
                                +- St.Label        message-group-title
                                +- St.Button       message-collapse-button

Up to GNOME 48 the list held a `NotificationSection` and a `MediaSection`, each
exposing a `_list` whose children were bins wrapping one message.

Since GNOME 49 notifications are grouped per source. The sections are gone, and
so is the flat list of messages: the actors carrying the `message` class now sit
two levels below a `NotificationMessageGroup`.

## Why the class has to land on the `message` actor itself

Every rule in the generated stylesheet is written `.openmenu.message` — a
compound selector, both classes on one actor. Putting `openmenu` on the group
instead matches nothing, and the failure is invisible: a probe asking "did any
actor get a class?" answers yes.

`messageActors()` therefore resolves what to theme **by style class, not by tree
position**: it walks down from the list and collects every descendant carrying
`message`, stopping at the first match on each branch. One expression covers 45
through 51 and does not care how deeply a future Shell nests them.

`messageContainers()` is its complement — every actor on the way down, excluding
the messages. Those are the actors that can gain children, so those are the ones
`trackMessageAdditions()` connects to, which is how a notification arriving into
an already-open menu still gets themed.

`MessageView` also holds a non-message `_overlay` child, a plain
`Clutter.Actor`. `has_style_class_name` exists only on `St.Widget`, so the walk
calls it with `?.` rather than assuming every actor is one.

## How this was established

By reading the live actor tree through `org.gnome.Shell.Eval` in the test
harness, not by reading the Shell's sources. Two earlier descriptions of this
structure, both derived from source reading, were wrong — the second while
correcting the first. `docs/superpowers/specs/2026-10-22-gnome-51-port-design.md`
records both in its review log.

A probe for this behaviour must raise a notification first, and must assert on
an actor that carries `message`. A headless session can present an empty list,
and a check that finds no message actor passes without having looked at
anything.

## Known gap: the group's own chrome

GNOME 49+ introduced `message-notification-group`, `message-group-header`,
`message-group-title` and `message-collapse-button`. None of the four appears
anywhere in `stylesheets.js`.

So notifications theme correctly, and the header and collapse button of each
group do not. Writing rules for them is theming design in a 3878-line generated
stylesheet, which is a different kind of work from a compatibility port; it is
tracked as its own ticket rather than folded into this one.
```

# 1. Port Open Bar to GNOME Shell 50 and 51 in this fork

Date: 2026-10-22

## Status

Accepted.

## Context

Upstream `neuromorph/openbar` has published nothing since 2025-10-05.
extensions.gnome.org advertises Shell versions 42 through 49. GNOME 50 and 51
are unsupported anywhere, and GNOME 51 is what this fork's maintainer runs.

Upstream's `main` is also broken: `clearBtn` was declared in two block scopes
and read outside both, so `applyMenuStyles` threw during `enable()` on every
Shell version. The fix exists in the version 49 payload on
extensions.gnome.org but was never pushed to git.

The sources are GPL-2.0-or-later, so forking and redistributing is permitted
provided the licence and the existing copyright notices are kept and
modifications are stated.

## Decision

Maintain the port in this fork, and offer it upstream as two separate pull
requests: the `clearBtn` fix first, since it stands alone and repairs every
version, then GNOME 50 and 51 support.

Keep the scope to compatibility. The six GTK widgets deprecated since 4.10 in
`prefs.js` still work in GTK 4.24 and are left alone; replacing them is an
interface rewrite, not a port.

Verify against a real Shell rather than by reading. `tools/verify-headless.sh`
starts a throwaway headless Shell and reports the state the Shell itself
assigns the extension.

## Consequences

The fork diverges from upstream until the pull requests land, and carries the
port forward at each Shell release. The verification harness makes that cheap:
the declaration is widened and the harness says whether anything else broke.

Three defects in the GNOME 49+ path were silent before the harness existed —
an unthemed Clear button, unthemed notifications, and a traversal that could
take the whole extension down. Compatibility by inspection would have missed
all three; two of them were found only by querying the live actor tree.

What inspection did establish, and the harness confirmed: no GI symbol, Shell
module export, private member, theme class name or GSettings key the extension
uses changed between 49 and 51.
